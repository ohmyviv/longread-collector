# Longread Collector v0.6 PR-5: Acquisition Service

Status: shadow architecture implementation  
Baseline: `collector-v0.6-pr4`  
Legacy control: `collector-v0.5.6m`  
Production integration: none

## 1. Purpose

PR-5 implements the v0.6 L3 **Acquisition Service**.  It replaces the implicit
legacy fallback control flow with an explicit, testable chain:

```text
Jina Reader
  -> if evidence is still insufficient: Direct HTML
  -> if evidence is still insufficient and budget allows: Firecrawl
```

PR-5 does not connect this chain to the active production pipeline.  The
production collector remains v0.5.6m.

The main design goal is not “extract as much text as possible”.  It is:

> stop acquiring as soon as the evidence is sufficient for the next downstream
> decision, and spend paid fallback only when another request can materially
> change the outcome.

## 2. Root cause addressed

The v0.5.6m extraction chain decides fallback mainly from `valid_body` and body
length.  That is too coarse.  A page can already contain enough evidence to
identify a training recap, event listing or program transcript even when the
body does not meet the legacy editor-length threshold.

This produced the audited Wuxi training case in which Jina and Direct HTML had
already obtained usable content but Firecrawl was still called before the page
was finally rejected as a training event.

PR-5 separates three different sufficiency questions:

- `sufficient_for_canonicalization`;
- `sufficient_for_editorial_judgment`;
- `sufficient_for_source_chase`.

A positive editorial or source-chase sufficiency result stops the chain.

## 3. Explicit extractor contract

All extractors implement the same port and return an immutable
`ExtractorPayload` containing observable facts only:

- body markdown/text;
- title, author and publication hint;
- canonical and outbound links;
- extractor metadata;
- latency, HTTP status and credits used.

Extractors do **not** decide:

- candidate disposition;
- page/editorial policy;
- whether another extractor should run;
- whether the item should occupy a portfolio slot.

Adapters are supplied for:

- existing `JinaReaderClient`;
- existing zero-credit Direct HTML reader;
- existing `FirecrawlClient`.

The Direct HTML implementation is imported lazily so importing the v0.6
acquisition package does not patch or activate legacy pipeline modules.

## 4. Sufficiency-aware stopping

The sufficiency evaluator uses body continuity, title evidence, paragraph
structure, deterministic decision cues and external-source links.

It is not a replacement Editorial Judge.  It only asks whether more extraction
is likely to change the downstream judgment.

Examples:

### Complete longform from Jina

```text
Jina -> sufficient_for_editorial_judgment = true -> STOP
```

Direct HTML and Firecrawl are not called.

### Training/event page already clear from Jina

A moderate body with multiple training/event/program/template cues can be
sufficient for editorial judgment even if it is shorter than the legacy editor
minimum.  Another scraper is unlikely to change the fact that it is a training
recap or event page.

```text
Jina -> sufficient_for_editorial_judgment = true -> STOP
```

### Jina partial, Direct HTML recovers article

```text
Jina -> insufficient
Direct HTML -> sufficient_for_editorial_judgment = true -> STOP
```

### External-link shell

If the page provides an external original-content link but not a judgeable body:

```text
Jina/Direct -> sufficient_for_source_chase = true -> STOP
```

The item proceeds as source-chase evidence rather than consuming Firecrawl just
to re-scrape the shell.

### Zero-cost extractors both insufficient

Only then may Firecrawl be considered.

## 5. Unified BudgetLedger

`BudgetLedger` enforces two hard resource classes before requests are sent:

1. acquisition-item ceiling, defaulting to `RunContext.max_acquisition_attempts`
   (currently 32);
2. Firecrawl daily and optional group request caps.

A Firecrawl reservation occurs before network execution.  A failed paid request
is not returned to the ledger.  This deliberately fails closed under
concurrency and prevents multiple tasks from simultaneously exceeding the hard
request limit.

The ledger records snapshots before and after each Firecrawl reservation.

PR-5 does not change the configured limits.  It only makes them explicit and
auditable.

## 6. Attempt-derived audit metrics

Every actual or skipped extractor step emits one
`StageEventType.EXTRACTOR_ATTEMPT` event with:

- extractor;
- `request_sent`;
- `request_outcome`;
- body/prose characters;
- latency and credits;
- fallback reason;
- expected information gain;
- budget snapshot before and after;
- sufficiency result;
- error information when applicable.

The final acquisition result emits one `ACQUISITION_RESULT` event.

Existing PR-1 event metrics therefore mechanically derive:

- extractor attempts;
- requests sent;
- request successes/failures;
- Firecrawl daily/group skips;
- selected successful extractor;
- cost.

No second Firecrawl success counter is maintained by Acquisition Service.  This
eliminates the dual-accounting pattern that previously allowed attempt logs and
run summaries to disagree.

## 7. Failure semantics

Extractor exceptions are converted into failed attempt events and do not escape
the stage unless the service itself has a programming error.

A failed Jina request can therefore fall through to Direct HTML.  A failed
Direct HTML request can fall through to Firecrawl if budget remains.

Budget denial is different from request failure:

```text
status = skipped
request_sent = false
request_outcome = skipped_daily_cap | skipped_group_cap
```

This distinction is preserved in StageEvent metrics.

## 8. Best-payload selection

The service keeps all successful payload candidates and selects the best bundle
using this order:

1. sufficient for editorial judgment;
2. sufficient for source chase;
3. sufficient for canonicalization;
4. metadata completeness;
5. prose length;
6. total body length.

The choice is a technical evidence choice, not an editorial candidate decision.

## 9. Test matrix

PR-5 includes zero-network tests for:

- Jina success stops Direct HTML and Firecrawl;
- training-event body stops without Firecrawl;
- Direct HTML recovery stops Firecrawl;
- Firecrawl runs only after both zero-cost routes remain insufficient;
- daily Firecrawl cap produces a skipped/no-request event;
- group Firecrawl cap produces a skipped/no-request event;
- external-link shell stops for source chase;
- the acquisition item cap prevents work beyond the configured ceiling;
- failed extractors fall through while preserving request-failure audit data;
- attempt events contain budget and expected-information-gain fields;
- Jina, Direct HTML and Firecrawl adapters normalize their existing client
  response shapes without network access.

## 10. Production safety boundary

PR-5 does **not**:

- edit legacy `pipeline*` modules;
- replace `_ORIGINAL_EXTRACT_ARTICLE` or any other module-global function;
- edit production classification or selection logic;
- edit Sheet/runtime configuration;
- write any Sheet rows;
- add a natural-run network call;
- increase Firecrawl budget;
- increase the 32-item acquisition ceiling;
- connect the 07:35 editor;
- enable automatic promotion.

`DEFAULT_V06_MANIFEST` advances only to:

```text
architecture_version = collector-v0.6-pr5
migration_phase = pr5_acquisition_service
```

All production-safety booleans remain false.

## 11. Migration implication

After PR-5, the next architecture step can adapt Discovery and the deterministic
Acquisition Gate to v0.6 contracts without first changing the production
collector.  Full parallel shadow remains a later PR.

The legacy extraction code remains available as control until v0.6 is validated
against natural holdout runs.

## 12. Definition of done

PR-5 is complete when:

1. Jina, Direct HTML and Firecrawl implement one explicit extractor contract;
2. successful sufficient evidence stops later extractors;
3. source-chase sufficiency stops unnecessary shell re-scraping;
4. Firecrawl is always budget-reserved before request send;
5. daily and group caps cannot be exceeded under concurrent reservation;
6. the 32-item cap is enforced by the ledger;
7. request outcomes are mechanically recoverable from StageEvents;
8. attempt logs and Firecrawl metrics use one source of truth;
9. all new tests and existing repository tests pass;
10. no active production behavior changes.
