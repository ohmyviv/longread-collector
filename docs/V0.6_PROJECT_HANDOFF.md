## 2. Settled target architecture

```text
Source Registry
      ↓
GitHub Collector
  ├─ L1 Discovery
  ├─ L2 Acquisition Gate
  ├─ L3 Acquisition
  └─ raw observations / replayable snapshots
      ↓
L4 Canonical Article
      ↓
L5 Editorial Judge
      ↓
Candidate Universe
      ↓
L6 Policy / Portfolio Selection
      ↓
history / archive / delivery
```

Responsibilities remain strict:

- **Collector / L1-L3**: discover leads, identify discovery surface, resolve article URL, acquire page/body, preserve raw evidence and replayable snapshots.
- **L4**: resolve canonical URL/source, publication date and provenance, source relationship, PageSurface, factual freshness.
- **L5**: editorial worth only.
- **L6**: policy, capacity, diversity and portfolio selection.

Non-negotiable separation:

> Collector outputs observations/evidence; L4 outputs resolved facts. Collector must not flatten uncertain date/source evidence into final canonical facts before L4.

Future primary Discovery authority is GitHub Collector. Scheduled ChatGPT/native discovery remains only a bounded transitional fallback and an independent audit/benchmark path. Do not build a second crawler inside the scheduled recommendation agent.

## 7. Phase 0B — source scheduling / rotation freshness

Detailed measurement:

```text
docs/benchmarks/2026-08-13_phase0b_freshness_measurement.md
```

### 7.1 Keep two clocks separate

```text
A. workflow delay
   scheduled_at -> actual Collector start

B. source revisit delay
   source scan -> article publication -> next source scan -> report cutoff
```

Across 11 recent natural scheduled runs from 2026-08-11 through the first post-Phase-0A run:

```text
workflow start delay median ~= 57m08s
workflow start delay p90    ~= 89m13s
workflow start delay max    =  93m30s
```

This is operationally material, but it is an amplifier rather than the primary demonstrated benchmark cause.

### 7.2 Current selector contract

Active config:

```text
native_source_scans_per_run = 8
```

The active config note explicitly describes approximately two days to cover the formal pool.

`select_sources_for_run()` currently implements:

```text
least-recently-scanned
+ priority-tier quota
+ same-day avoidance
```

With eight slots, the normal tier split is approximately:

```text
rotate: 6
explore: 2
```

The workflow provides two English-oriented and two Chinese-oriented Collector runs/day.

### 7.3 Capacity math

Current enabled registry size at measurement time:

```text
English: 29 enabled sources
Chinese: 34 enabled sources
```

At 16 native source slots/language/day:

```text
English full-pass floor ~= 29 / 16 = 1.81 days
Chinese full-pass floor ~= 34 / 16 = 2.13 days
```

Therefore a sub-24-hour revisit SLA for every enabled source—or even every current rotate source—is impossible under the existing slot capacity.

### 7.4 Anchor proof

Registered-source benchmark misses are consistent with this policy:

- **ProPublica**: scanned 2026-08-12 04:37; two benchmark pieces published later that day; neither 23:27 `intl_early` nor 04:28 `pre_report` rescanned ProPublica before cutoff.
- **Atlantic testosterone**: same pattern; healthy RSS route, no post-publication source scan before cutoff.
- **Atlantic AI panic**: published about 04:05 BJT; `pre_report` actually began around 04:28—after publication—but Atlantic still was not selected because older sources were ahead in LRU rotation. This directly separates source-selection failure from GitHub start delay.
- **Jiemian**: scanned 2026-08-12 13:23, article published 15:09, 18:45 `zh_evening` did not rescan it, next confirmed scan was 2026-08-13 18:50:41. Publication-to-next-scan lag was about 27h41m; same-day avoidance is directly relevant.
- **Yicai**: confirmed source scan interval from 2026-08-11 18:42 to 2026-08-13 18:50:41 was about 48h08m. Exact publication times of the two selected targets are unavailable, so do not fabricate exact article-to-scan lag.
- **Quanta** remains ambiguous for precise lag because exact publication time is unavailable and its relevant historical snapshot block was missing.

### 7.5 Phase 0B causal conclusion

For the registered-source anchor misses:

```text
coverage-oriented LRU
+ same-day avoidance
+ 8 source scans/run
+ large source pools
      ↓
1-2+ day revisit intervals
      ↓
article published after prior source scan
      ↓
no post-publication scan before report cutoff
      ↓
URL never reaches Collector observable universe
```

This is a **source revisit policy/capacity** problem first, not a proven route-quality, Acquisition, L4, or L5 problem.

### 7.6 Next repair direction

Do not blindly increase `native_source_scans_per_run` and do not merely remove same-day avoidance.

Under the existing eight-slot cap, the next design should split source selection conceptually into:

```text
freshness/SLA reserve
+
coverage rotation
```

A smaller explicit freshness-critical source class is required; the current rotate class is too large to guarantee sub-24-hour revisits under the existing budget.

Required properties of the next code PR:

- total selected sources/run remains <= active cap;
- bounded freshness reserve inside that cap;
- explicit source-policy configuration, not benchmark-URL hardcoding;
- overdue freshness-critical sources may bypass same-day avoidance;
- remaining slots preserve deterministic LRU rotate/explore coverage;
- no starvation of ordinary/explore sources;
- selection reason and scan age become observable;
- replay/simulation demonstrates improvement on the 2026-08-13 loss modes before natural activation.

### 7.7 Existing test contract found

`tests/test_native_discovery_v05.py` already asserts that the legacy scheduler:

```text
prefers unscanned/old sources
avoids same-day repeats
never selects monitor sources
```

The Phase 0B PR must therefore update behavior with explicit new tests rather than silently changing this invariant.

## 15. Current decision summary

Phase 0B has moved beyond the generic statement “sources were not rescanned.” The current scheduler is intentionally optimized for approximately two-day source-pool coverage, while the recommendation product needs materially tighter freshness for a smaller set of high-value sources.

The next engineering problem is therefore:

> Introduce an explicit, bounded freshness-critical source policy inside the existing source-scan cap, while retaining long-tail coverage and making the tradeoff observable.

Do not solve this by reopening PR-7.3, changing frozen L5, hiding NBD as an extractor problem, or simply doubling network work.
