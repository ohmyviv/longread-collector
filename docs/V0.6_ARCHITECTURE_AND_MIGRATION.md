# Longread Collector v0.6 architecture and migration plan

Status: architecture contract  
Baseline: `collector-v0.5.6m`  
Target mode: parallel shadow  
Production behavior in PR-0: unchanged

## 1. Decision

v0.5.6m remains the active legacy control. The next architecture is named
`collector-v0.6-shadow`; it does not continue the patch sequence as v0.5.6n.

PR-0 introduces only:

- this architecture contract;
- immutable v0.6 data contracts;
- a package and subpackage skeleton;
- a manifest describing migration state;
- fail-closed feature flags;
- contract and import-isolation tests.

PR-0 does **not**:

- change `pipeline_v054.py` or any active collector entrypoint;
- change `runtime_config.py` or Google Sheet configuration;
- enable v0.6 shadow or primary execution;
- perform additional discovery or extraction requests;
- increase the 32-attempt limit or Firecrawl budget;
- connect the 07:35 editor;
- permit automatic promotion.

## 2. Why the architecture changes

The legacy system has become observable and materially better at discovery,
extraction and audit, but its decision layers remain coupled.

The active v0.5.6m path depends on a wrapper chain and module-global replacement.
Page form, technical extraction quality, publication date, source identity,
editorial value and final policy action can overwrite one another. A single
mutable article object carries both factual fields and terminal decisions.

That structure produces three recurring failure modes:

1. a page feature, such as embedded video count, can override the written body;
2. failed acquisition can be mistaken for low editorial value;
3. static reserve thresholds can recover capacity without maximizing editorial
   value under the remaining budget.

v0.6 therefore separates facts, assessments and policy decisions.

## 3. Six-layer target architecture

```text
Discovery
  -> Acquisition Gate
  -> Acquisition
  -> Canonical Article
  -> Editorial Judge
  -> Policy & Portfolio Selection
```

Source chase is an explicit action emitted by Canonical Article or Policy and
fed back into Discovery or Acquisition. It is not a rejection reason.

### L1 Discovery

Question: what URLs and discovery evidence were found?

Responsibilities:

- run registered routes and open-web queries;
- preserve route, query, rank and source metadata;
- normalize URL hints;
- emit an immutable `DiscoveryRecord`.

It must not decide whether an item is a formal candidate.

### L2 Acquisition Gate

Question: should the system spend acquisition budget on this URL now?

Allowed hard rejects are limited to high-confidence, low-regret cases such as:

- login, captcha, homepage, listing, search and career pages;
- malicious or invalid URLs;
- exact known duplicates;
- high-confidence old items with authoritative date evidence;
- deterministic market-data cards or equivalent templates.

Unknown or conflicting dates must not become permanent rejects. Ambiguous items
are deferred or down-ranked.

### L3 Acquisition

Question: what body and metadata evidence can be obtained, at what cost?

The layer records every extractor attempt and returns an `AcquisitionBundle`.
It distinguishes:

- technical success;
- sufficiency for canonicalization;
- sufficiency for editorial judgment;
- sufficiency for source chase.

Firecrawl is allowed only when the expected information gain can change a
downstream decision. Run-level request metrics are derived from attempt events.

### L4 Canonical Article

Question: what content asset is represented by the page?

This layer resolves:

- page surface;
- main content medium;
- editorial genre;
- title, author and publication evidence;
- hosting source, canonical source and original publisher;
- source relationship and source action;
- duplicate cluster and freshness facts.

The following dimensions remain independent:

- `page_surface`: the web-page shell;
- `main_content_medium`: article, transcript, document, data card, and so on;
- `editorial_genre`: investigation, feature, analysis, event preview, promotion,
  and so on.

Embedded video count is evidence, not a terminal rule.

### L5 Editorial Judge

Question: how much editorial value and risk does the content have?

The judge emits continuous scores and a structured verdict. It does not emit
legacy `formal_candidate`, `special_candidate` or `reject` states.

Initial dimensions include:

- substance;
- original reporting;
- analysis and argument;
- evidence density;
- reader value;
- timeliness relevance;
- promotional, event, transcript and template risk.

A future model-based judge may implement the same interface for uncertain
items, but it cannot write final policy state.

### L6 Policy & Portfolio Selection

Question: given the current daily policy and limited budget, what action should
be taken?

Policy actions are:

- `select_standard`;
- `select_special`;
- `source_chase`;
- `defer`;
- `reject`.

Standard longreads, primary documents, academic material and source-chase
actions use separate tracks. Selection optimizes expected editorial utility,
risk, freshness, redundancy, diversity and cost.

The migration comparison keeps a 32-attempt ceiling. The v0.6 shadow selector
may use a 24+4+4 plan:

- 24 high expected-value attempts;
- 4 dynamic replacements based on observed results;
- 4 stratified exploration attempts to measure selection blind spots.

## 4. Contract principles

### 4.1 Immutable stage outputs

Each layer creates a new frozen result object. Downstream code must not mutate a
previous stage result in place.

### 4.2 One final projection

Only a future `FinalProjector` may derive legacy compatibility fields such as:

- `candidate_disposition`;
- `eligible_for_editor`;
- `reject_reason`;
- `canonical_source`;
- `source_action`.

This prevents top-level state, classification metadata and terminal state from
drifting.

### 4.3 Explicit dependency injection

The v0.6 orchestrator receives services through explicit constructor arguments.
Importing v0.6 must not modify legacy modules, module globals or active
entrypoints.

### 4.4 Evidence-backed decisions

Every decision contains structured evidence references. A conclusion can be
traced to the stage and observed value that produced it.

### 4.5 Technical, editorial and policy states are distinct

Technical status, flow status, editorial verdict and policy action use separate
enums. `eligible_for_editor` remains a compatibility projection only.

## 6. Legacy reuse map

The following assets are expected to be adapted rather than rewritten:

| Legacy asset | v0.6 destination |
|---|---|
| native discovery and effective routes | Discovery |
| Jina, direct HTML and Firecrawl clients | Acquisition extractors |
| content identity features | Canonical identity |
| publication date evidence | Canonical publication |
| source relationship evidence | Canonical source resolution |
| historical dedupe | Canonical dedupe |
| final recall audit | Audit and evaluation |
| Sheet read/write primitives | Persistence adapter |

The following remain frozen as legacy control during migration:

- `pipeline_v054.py`;
- `pipeline_v056f.py`;
- `pipeline_v056d.py`;
- `classification_v056m.py`;
- `extraction_v056m.py`;
- `staged_reserve_v056m.py`.

Only crashes, audit corruption, budget violations or security defects may be
fixed in legacy control while v0.6 is developed.

## 7. Migration pull requests

### PR-0: contract and skeleton

- architecture document;
- immutable contracts;
- manifest;
- fail-closed feature flags;
- package skeleton;
- tests proving defaults and import isolation.

No production behavior changes.

### PR-1: legacy adapter and stage events

Map legacy output to v0.6 contracts without changing decisions or making new
network calls. Derive run metrics from stage events.

### PR-2: canonical article

Implement page surface, medium, genre, publication, source relationship, source
action and duplicate identity. Replay known video/article, transcript, external
link and hosting-source failures.

### PR-3: editorial judge

Implement continuous scores and risk dimensions. Evaluate against human labels
without changing the primary selector.

### PR-4: policy and portfolio selector

Compare legacy 24+8 selection with expected-utility 24+4+4 on shared
acquisition results.

### PR-5: acquisition service

Implement sufficiency-aware stopping, a single budget ledger and attempt-derived
metrics. Remove extractor injection through global replacement.

### PR-6: discovery and acquisition gate

Adapt existing routes to the v0.6 contract and move only deterministic rejects
into the acquisition gate.

### PR-7: full parallel shadow

Share discovery snapshots and acquired bodies between legacy control and v0.6.
Do not duplicate Firecrawl requests.

### PR-8: controlled canary

After all gates pass, allow `v06_primary` for collector output while keeping
legacy shadow and the 07:35 editor isolated. Editor migration is a separate
manual decision.

## 8. Feature-flag safety

PR-0 defaults are deliberately fail-closed:

```text
pipeline_engine = legacy_v056m
v06_write_mode = events_only
v06_shadow_enabled = false
v06_primary_enabled = false
auto_promote_when_ready = false
editor_0735_connected = false
```

The v0.6 package is not imported by the active pipeline. Changing these Python
defaults alone does not alter production because no active runtime loader uses
them in PR-0.

Future activation requires:

1. an explicit runtime integration PR;
2. a reviewed configuration change;
3. a new natural shadow baseline;
4. manual promotion.

## 9. Evaluation system

Three data sets remain separate:

1. **Golden regression set**: known fixed cases used during development.
2. **Development replay set**: immutable discovery snapshots and cached bodies.
3. **Natural holdout**: runs occurring only after a version is frozen.

Selection exploration is required because unselected URLs generally lack body
truth. Shadow runs reserve a small exploration stratum to estimate missed value.

## 10. Release gates

### Discovery

- registered final discovery recall >= 75%;
- advancement target >= 85%.

### Acquisition gate

- deterministic hard-reject precision >= 98%;
- zero hard rejects of golden high-value articles.

### Acquisition

- zero unnecessary Firecrawl calls in reviewed samples;
- budget violations = 0;
- request detail and run summary closure = 100%.

### Canonical article

- publication field accuracy >= 95%;
- hosting/canonical/original relationship accuracy >= 95%;
- external-link source-chase recall >= 90%;
- article-versus-transcript medium accuracy >= 90%.

### Editorial judge and selection

- candidate precision >= 85%;
- serious false accepts = 0;
- actionable recall within attempted items >= 75%;
- editable final recall >= 60%;
- high-confidence selection regret reduced by at least 80% versus legacy.

### Promotion

All gates must pass for three consecutive natural shadow days. Promotion remains
manual, `auto_promote_when_ready` remains false, and the 07:35 editor remains
disconnected until a separate migration decision.

## 11. PR-0 definition of done

PR-0 is complete when:

1. v0.6 contracts import on Python 3.11+;
2. all stage result dataclasses are frozen and use tuple-based child collections;
3. feature flags default to legacy-only, events-only, no promotion and no editor
   connection;
4. unsafe flag combinations fail validation;
5. importing `longread_collector.v06` does not import or patch legacy pipeline
   modules;
6. no existing production file is modified;
7. tests pass;
8. the PR remains a draft until CI is reviewed.
